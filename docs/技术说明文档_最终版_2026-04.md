## 2. 系统的一句话定义

当前系统是一个以 `main.py` 为唯一主入口、以 `segment_id` 为多模态主键、以 `geo_sync` 为时空锚点、以 `Step 7.5 + design + deliverable` 为问题街道筛选主链、并以 `gis_export + web_sync` 面向 GIS 与网页消费的全景视频多模态空间诊断系统。

它不是单一模型脚本，而是一条由数据工程、时空对齐、统计特征、多模态建模、规则决策、人类监督、交付导出和可视化消费共同组成的完整分析链路。

## 3. 系统目标与核心功能

### 3.1 系统目标

系统面向的是“沿街移动拍摄视频”的空间环境诊断问题。目标不是只回答“画面里看到了什么”，而是回答：

1. 这段路空间上在哪里。
2. 这一小段路在视觉、声景、活动性、秩序感、舒适度上表现如何。
3. 多模态证据是否一致。
4. 哪些路段最值得优先关注。
5. 这些路段的问题更像是离散点，还是连续的“问题街道 / 问题路段”。
6. 最终如何把结果稳定导出到 GIS、地图网页、交付材料和后续治理流程中。

### 3.2 当前主要功能

当前项目已经具备以下正式功能：

1. 从原始视频抽取真实分析帧，并生成基础视觉/音频中间结果。
2. 生成真实 `segment_manifest.csv`，以 `segment_id` 作为后续所有阶段的统一主键。
3. 生成 `visual/segment_visual_features.csv`，把视觉证据聚合到 segment 层。
4. 生成 `geo_sync/frame_geo_metadata.csv` 与 `geo_sync/segment_geo_metadata.csv`，把视频、帧、segment 与 GPS 时空对齐。
5. 生成 `soundscape/audio_segment_features.csv`，从音频信号、事件类别、嵌入中提取 segment 级声景特征。
6. 生成 `fusion/segment_feature_table.csv` 与 `fusion/model_feature_table.csv`，形成可解释仓库表和建模表。
7. 运行 `agents` 阶段，形成标签无关的多智能体诊断证据。
8. 读取人工评分 `validation/final_annotation_labels_adjudicated.csv`，进入 Step 7.5 refined evaluation。
9. 基于 Step 7.5 refined outputs 与诊断证据，生成 `design/segment_priority_ranking.csv`，完成问题 segment 排序。
10. 将高优先级 segment 合并为 `deliverable/problem_episodes.csv`，形成更接近治理对象的连续问题路段。
11. 导出 `gis/frame_gis_export.csv`、`gis/segment_gis_export.csv`、`gis/problem_episode_gis_export.csv`，供 GIS 叠加和空间分析。
12. 导出 `web/sync_map_data.json`，支撑网页中的视频、图表、地图同步。
13. 提供 `/validation/<video_name>` 人工评分前端，直接写回 `final_annotation_labels_adjudicated.csv`。
14. 运行 `relationship` 研究层，输出跨模态关联矩阵、PLS 潜变量结果及对应图表。
15. 运行 `relationship/group_confirmatory` 研究层，输出理论分组后的 confirmatory 假设检验、稳健性分析及对应图表。
16. 运行 `proof` 研究层，把 Step 7.5 的 OOF 预测重组为成对增益、置信区间与 claim registry，并输出论文级证明图。
17. 运行 `paper_figures` 层，把 relationship 与 proof 的结果统一压缩成可直接用于论文正文或附录的四张正式图。

## 4. 核心设计原则

### 4.1 以 `segment_id` 为统一主键

本系统不是让视觉、音频、GPS、标签分别维护自己的切分方式，而是明确要求：

1. 先有真实 `segment_manifest.csv`。
2. 后续各阶段都围绕这张 manifest 对齐。
3. `segment_id` 是视觉、声景、融合、设计、交付、GIS、网页的统一主键。

这样做的科学意义是：避免多条分析链条在时间切分上互相漂移，保证各模态证据可以严格 merge，而不是“看起来差不多对齐”。

### 4.2 以真实分析帧为底层观测单位

当前系统正式规定：

- `VIDEO_FRAME_SKIP = 20`

这意味着：

1. 主程序每隔 20 个原始视频帧提取 1 张分析帧。
2. `geo_sync` 默认直接对齐 `output/<video>/frames/` 中这批真实分析帧。
3. `frame_geo_metadata.csv` 中的 `frame_index` 表示分析帧序号。
4. `video_frame_num` 表示对应的原始视频真实帧号，例如 `0, 20, 40, 60, ...`。

这样做的科学意义是：

1. 在成本可控的前提下保留稳定时序。
2. 避免对每一个原始帧都做高成本分析。
3. 保证“分析用帧”“空间对齐用帧”“网页联动用帧”“GIS frame 表”是同一套底层对象。

### 4.3 分析层与消费层分离

系统明确区分：

1. 分析层：segment、visual、geo_sync、soundscape、fusion、agents、Step 7.5、design、deliverable。
2. 消费层：gis_export、web_sync、validation 前端。

消费层不应改变分析结论，只负责组织、表达和导出已有结果。

### 4.4 显式处理坐标系

当前口径是：

1. `output_gps.csv` 中的权威坐标系是 `GCJ-02`。
2. `WGS84` 是近似逆变换后的派生坐标。
3. 导出与网页层都要保留双坐标字段。
4. 当前中国本地底图优先建议使用 `GCJ-02` 进行显示对齐。

这样做的科学意义是：避免把中国加偏坐标误当作全球通用坐标，导致网页、GIS、地图对齐全部出现系统性偏差。

### 4.5 人类评分是监督层，不是可有可无的装饰

当前项目不是一个“完全无监督自动给出最终问题街道”的系统。它的正式监督文件是：

- `output/<video_name>/validation/final_annotation_labels_adjudicated.csv`

系统允许自动 bootstrap 初稿、允许单次人工评分版，但最终正式问题路段筛选的语义锚点仍然来自人工评分。

这样做的科学意义是：

1. 舒适度、活力度、问题严重度、首要问题标签本质上都包含价值判断。
2. 纯机器输出可作为证据，但不能天然替代最终监督标签。
3. 通过人类评分把“感知质量”从隐含概念变成可学习、可复核、可解释的目标变量。

## 5. 核心数据层级

### 5.1 Frame 层

Frame 层是最细的观测层，但这里的 frame 不是每个原始视频帧，而是“主程序真实抽出的分析帧”。

典型文件：

- `frames/frame_*.jpg`
- `geo_sync/frame_geo_metadata.csv`
- `gis/frame_gis_export.csv`

Frame 层适合回答：

1. 当前时刻在哪。
2. 当前时刻看到什么。
3. 当前时刻的声景和问题状态挂在哪个 segment 上。

### 5.2 Segment 层

Segment 是正式分析主单位。

典型文件：

- `segments/segment_manifest.csv`
- `visual/segment_visual_features.csv`
- `soundscape/audio_segment_features.csv`
- `fusion/segment_feature_table.csv`
- `fusion/model_feature_table.csv`
- `geo_sync/segment_geo_metadata.csv`

Segment 层适合回答：

1. 这一小段路整体怎么样。
2. 视觉、声景、空间位置、标签是否一致。
3. 这一段是否值得作为问题候选。

### 5.3 Problem Episode 层

Episode 不是基础分析天然存在的层，而是把高优先级 segment 合并后得到的“连续问题路段对象”。

典型文件：

- `deliverable/problem_episodes.csv`
- `deliverable/problem_episode_summary.csv`
- `gis/problem_episode_gis_export.csv`

Episode 层适合回答：

1. 连续的一段街道是否构成一个治理单元。
2. 哪几段 segment 本质上属于同一个问题走廊。
3. 应该向交付、治理、展示层输出哪些连续问题对象。

### 5.4 GIS / Web 消费层

GIS 和网页不是新的分析层，而是消费层。

典型文件：

- `gis/*.csv`
- `web/sync_map_data.json`

这一层的任务是把上游分析结果转成可以直接用于 GIS 软件、地图网页、人工核查和展示交互的数据结构。

## 6. 当前唯一主入口与正式流程

### 6.1 当前唯一主入口

当前系统推荐的唯一主入口是：

- `main.py`

其它脚本可以存在，但都不应被视为主流程入口。

### 6.2 正式主流程顺序

当前单视频正式顺序为：

1. 基础视觉 / 音频处理
2. `segment`
3. `visual`
4. `geo_sync`
5. `soundscape`
6. `fusion`
7. `agents`
8. `design`
9. `deliverable`
10. `gis_export`
11. `web_sync`

此外，Step 7.5 refined evaluation 是连接 `fusion`、`validation` 与 `design` 的关键监督建模层。它通常在已有输出基础上通过独立命令运行，而不是每次都要求全量 fresh run。

再往后还有一条独立的“研究证据支线”，通常不改变治理排序结果，而是在已有稳定产物之上追加学术图层：

1. `relationship`
2. `relationship/group_confirmatory`
3. `proof`
4. `paper_figures`

其中：

1. `relationship` 主要消费 `fusion/model_feature_table.csv`、`fusion/model_feature_dictionary.json`、`segments/segment_manifest.csv`。
2. `group_confirmatory` 建立在 `relationship` 和 `fusion` 之上，做理论驱动的组级 confirmatory 检验。
3. `proof` 建立在 `fusion_eval_refined` 的 OOF 预测之上，做 paired delta 与 claim registry。
4. `paper_figures` 同时消费 `relationship/group_confirmatory` 与 `proof` 的结果，生成最终论文图包。

### 6.3 典型运行模式

当前系统支持三类典型运行模式：

1. `fresh run`
   - 从原始视频出发跑完整链路。
2. `from_existing_output`
   - 基于已有输出只补跑缺失或下游阶段。
3. 独立尾链运行
   - 例如只运行 Step 7.5、只运行 design、只运行 deliverable、只运行 web_sync 或 gis_export。

这种设计的科学性在于：

1. 最大复用已有结果。
2. 避免高成本阶段重复运行。
3. 允许人工评分、GIS 导出、网页同步等尾链工作独立迭代。

## 7. 各阶段详细说明：功能、输入输出与科学性

### 7.1 基础视觉 / 音频处理

#### 功能

这一层负责把原始视频转成后续所有阶段共享的基础资产，包括：

- `frames/`
- `stats/`
- `ai_evaluation/`
- `audio_events/`
- 视配置可能还有 `split/`、`mask/`、`overlay/`、`reproj/` 等中间结果

#### 核心输入

- 原始视频文件

#### 核心输出

- 真实分析帧
- 帧级统计
- 帧级 AI 评价
- 音频事件时间轴

#### 科学性

这一层的科学性不在于某个单一模型，而在于它完成了“从连续媒体到可分析观测序列”的转换：

1. 把原始视频转成稳定采样的分析帧序列。
2. 为后续所有多模态阶段建立统一时间轴。
3. 把不可直接复核的连续信号拆成可保存、可重用、可核查的中间结果。

### 7.2 Segment 阶段

#### 功能

`segment` 阶段生成：

- `segments/segment_manifest.csv`

它定义了整个系统后续使用的真实 `segment_id` 体系。

#### 核心输入

- 真实分析帧与其时间位置

#### 核心输出

- `segment_id`
- `start_time_sec`
- `end_time_sec`
- `center_time_sec`
- `included_frame_indices`
- `included_frame_paths`

#### 科学性

Segment 是一种“中尺度聚合单元”。相比 frame 它更稳、相比整条视频它更细，因此：

1. 能够减少单帧噪声。
2. 又能保留局部空间问题的分辨率。
3. 适合做多模态融合和人工评分。

系统规定人工评分单位是 segment，而不是 frame 或 episode，也正是因为 segment 在“稳定性”和“可定位性”之间取得了更好的平衡。

### 7.3 Visual 阶段

#### 功能

`visual` 阶段生成：

- `visual/segment_visual_features.csv`

当前实现优先复用已有帧输出与 AI 活动分数，不重新跑大模型。

#### 核心输入

- `segments/segment_manifest.csv`
- `frames/frame_*.jpg`
- `ai_evaluation/activity_scores.csv`

#### 核心输出

当前视觉表至少包含：

1. 基础对齐字段
   - `segment_id`
   - `start_time_sec`
   - `end_time_sec`
   - `center_time_sec`
   - `included_frame_count`
2. 视觉统计字段
   - 亮度、饱和度、对比度
   - 绿视率
   - 天空蓝占比
   - 暖色/冷色/灰色/暗部比例
   - 边缘密度
   - 灰度熵
3. AI 活动聚合字段
   - `ai_activity_*_score_mean`
   - `ai_activity_major_label`
   - `ai_activity_suitable_labels`

#### 科学性

这一层的科学性来自两个方面：

1. 使用明确、可解释、可复算的视觉统计量，而不是只依赖黑箱情感标签。
2. 所有视觉结果都明确聚合到 manifest 定义的真实 segment 上，避免人为再造一套切分逻辑。

因此 visual 阶段既能为 GIS 和网页提供稳定的“视觉画像”，又能为后续建模和诊断提供透明的视觉证据。

### 7.4 Geo Sync 阶段

#### 功能

`geo_sync` 阶段负责把视频时间轴与 GPS 时间轴对齐，生成：

- `geo_sync/frame_geo_metadata.csv`
- `geo_sync/segment_geo_metadata.csv`
- `geo_sync/geo_sync_summary.json`

#### 核心输入

- 视频文件
- `output_gps.csv`
- `frames/`
- `segments/segment_manifest.csv`

#### 当前正式口径

1. 权威坐标系：`GCJ-02`
2. 派生坐标系：`WGS84`
3. 默认对齐方式：优先对齐 `output/<video>/frames/` 中的真实分析帧
4. 当前默认：
   - `VIDEO_FRAME_SKIP = 20`
   - `GEO_SYNC_ALIGN_TO_ANALYSIS_FRAMES = True`

#### 科学性

Geo Sync 的科学性体现在：

1. 不是再采一套独立帧，而是对齐主程序真实分析帧，保证空间锚点与视觉观测严格一致。
2. 显式保留 `GCJ-02` 与 `WGS84` 双坐标，不混淆权威坐标与派生坐标。
3. 对 `frame` 和 `segment` 两个层级都生成空间元数据，使后续 GIS、网页、问题路段定位可以共用同一套空间基础。

### 7.5 Soundscape 阶段

#### 功能

`soundscape` 阶段生成：

- `soundscape/audio_segment_features.csv`
- `soundscape/audio_feature_meta.json`

#### 核心输入

- `segments/segment_manifest.csv`
- `audio_events/` 时间轴
- 提取出的音频波形

#### 当前特征结构

当前 soundscape 不是只做单一标签，而是混合三类证据：

1. 低层信号特征
   - RMS
   - ZCR
   - spectral centroid / bandwidth / rolloff
   - tempo
   - silence ratio
2. 事件语义特征
   - top-k events
   - event group ratios: traffic / human / nature / mechanical / other
3. 嵌入特征
   - PANNs embedding
   - top labels / top scores

#### 科学性

声景质量不可能仅由“响不响”决定，因此 soundscape 采用多层表示：

1. 低层信号回答“物理声学强度和结构是什么”。
2. 事件组回答“听到了什么来源”。
3. 嵌入回答“更复杂的语义模式是什么”。

这比单一 loudness 指标更科学，也更适合解释“热闹”和“吵闹”并不等价这一现实问题。

### 7.6 Fusion 阶段

#### 功能

`fusion` 阶段生成：

- `fusion/segment_feature_table.csv`
- `fusion/model_feature_table.csv`
- `fusion/feature_dictionary.json`
- `fusion/model_feature_dictionary.json`

#### 两张核心表的区别

1. `segment_feature_table.csv`
   - 更接近解释型仓库表。
   - 保留各模态来源和更人类可读的字段。
2. `model_feature_table.csv`
   - 更接近建模矩阵。
   - 用于 Step 7 / Step 7.5 的模型训练与评估。

#### 科学性

Fusion 的科学性不是“把所有特征堆到一起”，而是：

1. 先把多模态证据整理成显式、可追溯的特征仓库。
2. 再把适合建模的数值矩阵单独导出。
3. 通过 feature dictionary 保存特征来源与语义，避免后续模型解释失去可追溯性。

因此 fusion 是“结构化多模态证据层”，而不是一刀切地宣称融合一定优于单模态。

### 7.7 Agents 阶段

#### 功能

`agents` 阶段是 Step 6 多智能体诊断层，主要输出：

- `diagnostics/segment_profiles.jsonl`
- `diagnostics/segment_diagnosis.jsonl`
- `diagnostics/segment_critic_reviews.jsonl`

#### 当前角色结构

从代码看，当前多智能体编排器主要包括：

1. `SegmentProfilerAgent`
2. `SoundscapeInterpreterAgent`
3. `CrossModalDiagnosticianAgent`
4. `CriticAgent`

#### 关键约束

这一层是明确“标签无关”的：

1. 不读取人类评分文件。
2. 只读取 segment、soundscape、fusion 等既有分析结果。
3. 其作用是把多模态证据组织成更可读、更可用于后续设计的诊断语义。

#### 科学性

Agents 阶段的科学性不在于“把 LLM 当真值”，而在于：

1. 它把结构化特征转译为人类更容易理解的诊断解释。
2. 它是标签无关的，因此不会把人工监督污染进前置证据。
3. 它为后续 design 提供跨模态原因解释，而不是直接替代评分或排序。

### 7.8 Validation / Adjudication 阶段

#### 功能

Validation 是人类监督层。当前正式主文件是：

- `validation/final_annotation_labels_adjudicated.csv`

#### 当前人工评分单位

评分单位是 `segment`，不是 frame，也不是 episode。

#### 当前正式字段

当前下游稳定使用的字段包括：

- `segment_id`
- `street_type`
- `comfort_score`
- `vitality_score`
- `soundscape_pleasantness`
- `soundscape_eventfulness`
- `overall_problem_severity`
- `main_problem_labels`
- `primary_problem_label`
- `confidence_score`
- `annotator_notes`

#### 关于旧版双评审 / reliability / adjudication 链

历史上 validation 还可以包含：

- validation pack
- reliability report
- adjudication pack
- final adjudication finalize

这些中间产物仍然有价值，但当前 Step 7.5 / design / deliverable 的硬依赖已经收敛到：

- `final_annotation_labels_adjudicated.csv`

也就是说，系统当前真正需要的是“最终标签文件”，而不是必须把所有旧中间文件都重新走一遍。

#### 科学性

Validation 的科学性在于：

1. 把抽象的“感受”变成明确监督变量。
2. 让舒适度、活力度、声景事件性、问题严重度这些主观但重要的目标获得明确标注。
3. 为后续 Step 7.5、design、deliverable 提供可复核的监督基线。

### 7.9 Step 7.5 Refined Evaluation

#### 功能

Step 7.5 是当前正式“模型证据层”，生成：

- `fusion_eval_refined/per_target_metrics_refined.csv`
- `fusion_eval_refined/model_comparison_refined.csv`
- `fusion_eval_refined/bootstrap_ci_refined.json`
- `fusion_eval_refined/oof_predictions_refined.csv`
- `fusion_eval_refined/feature_screening_registry.json`
- `fusion_eval_refined/permutation_importance.csv`
- `fusion_eval_refined/shap_summary_refined.csv`
- `fusion_eval_refined/step75_summary.md`

#### 主要输入

1. `fusion/model_feature_table.csv`
2. `fusion/model_feature_dictionary.json`
3. `validation/final_annotation_labels_adjudicated.csv`

#### 当前目标变量口径

从代码看，Step 7.5 当前分三类目标：

1. confirmatory regression targets
   - `comfort_score`
   - `vitality_score`
   - `soundscape_eventfulness`
2. exploratory regression targets
   - `safety_score`
   - `overall_problem_severity`
   - `soundscape_pleasantness`
3. exploratory classification targets
   - `primary_problem_label`

#### 当前建模和评估策略

这一层的核心不是“训练一个模型”，而是建立一个稳健、可解释、抗泄漏的证据层：

1. **标签 schema 检查**
   - 检查目标列是否存在。
   - 检查数值列非空样本是否足够。
   - 检查数值评分是否落在 1~5 合理区间。
2. **特征筛选**
   - 去掉缺失率过高特征：`> 0.95`
   - 去掉近零方差特征：`<= 1e-12`
   - 去掉过高相关特征：`> 0.95`
   - 再按目标相关性做组内排名
3. **泄漏安全的折内筛选**
   - 筛选发生在 CV fold 内，而不是先用全数据筛选再评估。
4. **重复交叉验证**
   - 回归默认 `5-fold × 20 repeats`
   - 分类按类别支持度做分层折叠
5. **稀有类别处理**
   - `primary_problem_label` 若类别过稀，会合并到 `mixed_or_unclear`
   - 如果合并后仍不满足类支持度，则跳过该分类目标
6. **Bootstrap 置信区间**
   - 默认 `2000` 次 bootstrap
7. **解释性**
   - permutation importance
   - SHAP summary（可用时）

#### 科学性

Step 7.5 的科学性主要体现在：

1. **不把训练分数当结论，而把模型结果作为证据层。**
2. **避免信息泄漏。**
3. **承认小样本高维场景的现实，先做保守筛选再评估。**
4. **通过重复 CV 与 bootstrap，强调稳定性而不是单次幸运结果。**
5. **通过 permutation / SHAP，把“模型会预测”转化为“为什么会预测”。**

因此，Step 7.5 不是最终问题街道筛选器，而是为 design 提供稳健的多模态模型证据。

### 7.10 Design 阶段

#### 功能

`design` 阶段是 Step 8 设计映射层，主要输出：

- `design/segment_priority_ranking.csv`
- `design/step8_evidence_registry.json`
- `design/design_plan.jsonl`
- `design/intervention_matrix.csv`
- `design/edit_prompts.jsonl`
- `design/step8_design_summary.md`

#### 主要输入

1. diagnostics
2. `fusion/model_feature_table.csv`
3. `fusion_eval_refined/*`
4. `validation/final_annotation_labels_adjudicated.csv`
5. `soundscape/audio_segment_features.csv`
6. `segments/segment_manifest.csv`

#### 当前真正做的事

Design 阶段不是简单复制 Step 7.5 分数，而是把多种证据转成透明的 segment 排序：

1. 从多模态证据推断设计导向的 `street_type`
   - `commercial_social`
   - `transport_movement`
   - `leisure_cultural`
   - `mixed_uncertain`
2. 计算几个核心中间量
   - `diagnosis_severity`
   - `comfort_risk_score`
   - `vitality_deficit_score`
   - `eventfulness_risk_or_gap`
   - `multimodal_consistency_score`
   - `evidence_strength_score`
3. 计算最终 `priority_score`

#### 当前优先级排序公式

从 `priority_ranker.py` 可见，当前核心分数是：

`priority_score = 0.30 * diagnosis_severity + 0.18 * label_severity_score + 0.24 * confirmatory_need_score + 0.14 * consistency_score + 0.14 * evidence_score`

其中：

1. `diagnosis_severity`
   - 来自多智能体诊断严重度；若缺失则退回舒适度 proxy。
2. `label_severity_score`
   - 来自人评 `overall_problem_severity`。
3. `confirmatory_need_score`
   - 由 comfort risk、vitality deficit、eventfulness gap 组合而成。
4. `consistency_score`
   - 衡量视觉与声景是否互相印证，例如：
     - 人流视觉 vs 人声
     - 车流视觉 vs 交通/机械声
     - 绿视率 vs 自然声
     - 活力度视觉 vs 人声/音乐
5. `evidence_score`
   - 衡量诊断、profile、标签、模型特征、Step 7.5 证据是否齐备。

#### 街道类型与目标调制

Design 不是用统一全局标准看所有路段，而是街道类型调制：

1. 对不同街道类型设置不同的“期望活力度范围”和“期望事件性范围”。
2. 因此系统区分：
   - “太安静导致缺活力”
   - “过度嘈杂导致失控”
3. 这使得“热闹”不会被机械等同为“差”，也不会把所有街道都往同一个理想状态拉。

#### 科学性

Design 阶段的科学性在于：

1. 它不是纯模型分数排序，而是多证据透明加权。
2. 它把“问题街道”定义为需要干预的综合优先级，而不是某一个单独模态异常。
3. 它把街道类型差异纳入逻辑，避免一刀切评价。

### 7.11 Deliverable 阶段

#### 功能

Deliverable 是把 design 的 segment 级结果组织成更接近治理对象的连续问题路段，输出：

- `deliverable/problem_episodes.csv`
- `deliverable/problem_episode_summary.csv`
- `deliverable/problem_episode_evidence.csv`
- `deliverable/problem_episode_prompts.csv`
- 以及 HTML / PDF / 卡片类交付物（按配置）

#### 当前算法逻辑

Deliverable 包括两步：

1. **选段**
   - 可按 `top_k`
   - 可按 `top_percent`
   - 可按 `priority_threshold`
   - 若都没给，则默认回退 `DEFAULT_TOP_K = 12`
2. **合并成 episode**
   - 若相邻高优先级 segment 的时间间隔足够小，则合并
   - 或者时间重叠比例超过阈值，也合并
   - 当前默认重叠比例阈值：`0.20`

#### 代表片段选择

Episode 内并不是随便挑一个 segment 作为代表，而是：

1. 先找 episode 中高优先级候选。
2. 在接近最高优先级的候选里，优先选离 episode 中心时间更近的段。
3. 再生成 hero frame 与代表帧 triplet。

#### 科学性

Deliverable 的科学性在于：

1. 真实治理对象往往不是单个离散 segment，而是连续走廊问题。
2. 时间连续或重叠的高优先级 segment 很可能属于同一空间问题。
3. 用 episode 表达比只给很多离散点更接近现实治理单元。

### 7.15 Relationship 阶段

#### 功能

`relationship` 阶段是在既有 `fusion`、`soundscape` 与 `segment` 产物之上追加的跨模态研究层，负责生成：

- `relationship/feature_registry.csv`
- `relationship/feature_correlation_matrix_spearman.csv`
- `relationship/feature_correlation_matrix_dcor.csv`
- `relationship/feature_correlation_pvalues.csv`
- `relationship/feature_correlation_qvalues.csv`
- `relationship/significant_pairwise_links.csv`
- `relationship/pls_latent_summary.csv`
- `relationship/pls_x_loadings.csv`
- `relationship/pls_y_loadings.csv`
- `relationship/pls_bootstrap_stability.csv`
- `relationship/pls_permutation_test.json`
- `relationship/figures/fig1` 至 `fig4`
- `relationship/relationship_summary.md`

#### 主要输入

- `fusion/model_feature_table.csv`
- `fusion/model_feature_dictionary.json`
- `soundscape/audio_segment_features.csv`
- `segments/segment_manifest.csv`

#### 当前真正做的事

1. 先用 `prepare_cross_modal_feature_table()` 对 `model_feature_table.csv` 做保守筛选，只保留可用于视觉-音频关系分析的数值特征。
2. 把 segment 按 `segment_manifest.csv` 的时序重新排序，建立 chronology-aware 的分析序列。
3. 对视觉特征与音频特征做两类成对关联：
   - Spearman 秩相关；
   - dCor 距离相关。
4. 用 `circular_block_permutations()` 进行 block-shift permutation，避免把高度相邻、彼此重叠的 segment 误当成独立样本。
5. 再构造 thin subset，只保留时间序列中每隔一个 segment 的样本，作为 non-overlap sensitivity check。
6. 在 pairwise 之外，再做 PLSCanonical，把高维视觉和音频特征压缩为少数潜变量，检查是否存在稳定的低维耦合结构。

#### 科学性

Relationship 层的科学性主要体现在：

1. 它不是直接在所有字段上暴力相关，而是先做保守特征筛选，降低伪相关与文本列污染。
2. 它显式考虑相邻 segment 的时间依赖性，用 block-shift permutation 而不是把样本当成完全独立。
3. 它同时报告 full sample 与 thin sample，避免“相关性只来自重叠窗口”的误判。
4. 它同时保留 pairwise 证据与 PLS 潜变量证据，使“局部关联”和“整体耦合”两条证据链可以互相补充。

### 7.16 Group Confirmatory 阶段

#### 功能

`relationship/group_confirmatory` 阶段负责把细粒度 pairwise 结果提升为理论驱动、可写入正文的组级 confirmatory 检验，输出：

- `relationship/group_confirmatory/group_definition_registry.csv`
- `relationship/group_confirmatory/group_composites.csv`
- `relationship/group_confirmatory/group_composite_diagnostics.csv`
- `relationship/group_confirmatory/hypothesis_registry.csv`
- `relationship/group_confirmatory/group_pair_tests_full.csv`
- `relationship/group_confirmatory/group_pair_tests_thin.csv`
- `relationship/group_confirmatory/group_pair_tests_combined.csv`
- `relationship/group_confirmatory/leave_one_feature_out_robustness.csv`
- `relationship/group_confirmatory/time_trend_sensitivity.csv`
- `relationship/group_confirmatory/confirmatory_claim_registry.csv`
- `relationship/group_confirmatory/figures/*`
- `relationship/group_confirmatory/group_confirmatory_summary.md`

#### 主要输入

- `fusion/model_feature_table.csv`
- `fusion/model_feature_dictionary.json`
- `segments/segment_manifest.csv`
- `relationship/feature_registry.csv`
- `relationship/significant_pairwise_links.csv`
- `relationship/pls_latent_summary.csv`

#### 当前真正做的事

1. 先按固定规则把视觉特征与音频特征组合成可解释 group，例如：
   - `people_presence`
   - `green_nature`
   - `traffic_road_hardscape`
   - `audio_signal_level`
   - `audio_event_human`
   - `audio_event_natural`
2. 每个 group 内部先做 winsorize、z-score、符号对齐，再取等权均值得到 composite。
3. 构造小规模 confirmatory family，目前固定为 H1-H5 五条核心假设。
4. 对每条假设同时做：
   - full sample 的 block-shift permutation；
   - thin sample 的方向一致性检验；
   - leave-one-feature-out 稳健性分析；
   - time-trend sensitivity。
5. 最终把每条假设归类为：
   - `supported_confirmatory`
   - `directionally_consistent_but_not_significant`
   - `unstable_under_sensitivity`
   - `not_supported`
   - `not_testable`

#### 科学性

Group confirmatory 层的科学性在于：

1. 它把高维、强多重比较负担的 pairwise 分析压缩成少量理论预注册式假设。
2. 它不是只看 p 值，而是把方向一致性、置信区间、LOFO 稳健性、thin subset 一致性都纳入 claim 规则。
3. 它让“可解释组”成为主角，便于后续论文和治理叙事，而不是停留在单个 feature 的偶然相关上。

### 7.17 Proof 阶段

#### 功能

`proof` 阶段是对 Step 7.5 refined evaluation 的“证据重表达”，不是重训练模型。它输出：

- `proof/proof_model_comparison.csv`
- `proof/proof_paired_deltas.csv`
- `proof/proof_bootstrap_ci.csv`
- `proof/proof_permutation_tests.csv`
- `proof/proof_claim_registry.csv`
- `proof/figures/fig5_fusion_delta_forest.*`
- `proof/figures/fig6_oof_performance_by_target.*`
- `proof/proof_summary.md`

#### 主要输入

- `fusion_eval_refined/oof_predictions_refined.csv`
- `segments/segment_manifest.csv`
- `fusion_eval_refined/per_target_metrics_refined.csv`
- `fusion_eval_refined/model_comparison_refined.csv`
- `fusion_eval_refined/step75_summary.md`

#### 当前真正做的事

1. 把 Step 7.5 的 OOF 预测按 `segment_id + target_name + model_group` 聚合为 segment 级预测。
2. 对回归目标计算 `MAE / RMSE / Spearman`，对分类目标计算 `Brier / balanced accuracy / ROC-AUC`。
3. 在同一 segment 内比较 fusion 与 baseline 的损失差，得到 `delta_loss`。
4. 用 block bootstrap 计算 95% 置信区间，用 block sign-flip test 计算 permutation p 值。
5. 再把 full subset 与 thin subset 结合，给每个 target 分配 claim label：
   - `fusion_superior_to_both`
   - `fusion_complementary_but_not_superior`
   - `no_evidence_fusion_better`
   - `single_modality_stronger`

#### 科学性

Proof 层的科学性在于：

1. 它比较的是同一 segment 上的 paired loss，而不是不同模型在不同切分上“平均看起来更好”。
2. 它显式保留不确定性区间和 q 值，避免把轻微数值优势过度解读为“fusion 必胜”。
3. 它把 thin subset 作为额外敏感性检验，因此 claim label 更保守。

Paper figures 层的科学性在于：

1. 图不是凭视觉美观临时拼接，而是严格消费已经落盘的 research/proof 证据表。
2. 统一颜色、符号和方向约定后，读者可以在一组图里连续比较 relationship 证据与 proof 证据。
3. 这一层不创造新结论，只做证据压缩与规范表达。

## 8. “问题街道”是如何筛选出来的

这是整个系统最关键的核心问题。

### 8.1 先说明：问题街道不是某一个阶段单独“猜出来”的

当前系统中的“问题街道”是分层得到的：

1. 在 segment 层，得到多模态证据。
2. 在 validation 层，得到人工监督标签。
3. 在 Step 7.5 层，得到稳健模型证据。
4. 在 design 层，得到 segment 级优先级排序。
5. 在 deliverable 层，把连续高优先级 segment 合并为 problem episode。

因此“问题街道”不是单个黑箱模型的输出，而是一个多阶段、可解释、可回溯的筛选结果。

### 8.2 证据层：先知道这段路客观上像什么

系统先积累以下证据：

1. 视觉结构
   - 绿视率、道路/建筑/车辆/人等比例
2. 声景结构
   - 交通、人声、自然、机械等事件组比例
3. 活动结构
   - walking / standing / sitting / shopping 等线索
4. 空间位置
   - 真实路线坐标
5. 多智能体诊断
   - 对跨模态问题的自然语言解释

这一步的目的不是直接给出“问题”标签，而是把环境状态尽量客观、结构化地描述出来。

### 8.3 监督层：用人评定义“什么叫问题”

系统通过 `final_annotation_labels_adjudicated.csv` 引入人类监督。

当前真正用来定义问题街道的核心监督变量包括：

1. `overall_problem_severity`
2. `primary_problem_label`
3. `comfort_score`
4. `vitality_score`
5. `soundscape_pleasantness`
6. `soundscape_eventfulness`

这一步的科学性在于：

1. “问题街道”不是纯物理量，而是感知、秩序、舒适与风险的综合概念。
2. 必须由人类评分提供目标语义锚点。

### 8.4 模型证据层：Step 7.5 负责回答“多模态证据能否稳定支持这些标签”

Step 7.5 不直接筛选问题街道，而是回答：

1. 哪些特征组对各类监督目标有稳定预测力。
2. 单模态与多模态的相对表现如何。
3. 重要特征是否稳定、是否具有解释性。

因此 Step 7.5 的输出是“证据”，不是最终治理排序。

### 8.5 设计排序层：真正把问题程度转成 segment 优先级

真正决定“哪个 segment 更值得优先处理”的是 `design/segment_priority_ranking.csv`。

当前排序逻辑是：

1. 利用人评严重度和首要标签提供监督信号。
2. 利用多智能体诊断提供问题严重度解释。
3. 利用舒适度风险、活力度缺口、事件性失衡构造 confirmatory need。
4. 利用多模态一致性和证据齐备度控制排序可信度。

这样筛出来的高优先级 segment，才是“问题街道候选段”。

### 8.6 交付层：把离散 segment 合并成连续问题路段

治理对象通常不是“第 37 段片段”，而是“一整段从 A 到 B 的问题街道”。

因此 deliverable 阶段会：

1. 选出高优先级 segment。
2. 按时间邻接或重叠关系合并。
3. 形成 `problem_episodes.csv`。

这一步让结果从“模型排序”变成“可治理路段对象”。

### 8.7 最终结论

当前系统中的“问题街道”有两个正式层级：

1. **segment 级问题候选**
   - 来源：`design/segment_priority_ranking.csv`
2. **episode 级连续问题街道**
   - 来源：`deliverable/problem_episodes.csv`

其中：

1. segment 级用于细粒度分析和排序。
2. episode 级用于交付、GIS 和治理表达。

## 9. 每一步“科学性”总结

### 9.1 为什么先抽帧再分析

因为原始视频是连续信号，不适合直接作为多模态结构化分析对象。稳定抽样可以在成本、时序精度和可复核性之间取得平衡。

### 9.2 为什么用 segment 而不是 frame 作为主评分单位

因为：

1. 单帧噪声太大。
2. episode 又太粗。
3. segment 最适合做人评、多模态融合和空间定位。

### 9.3 为什么 geo_sync 必须对齐真实分析帧

因为如果空间层和视觉层不是同一批帧，后续 GIS、网页、问题定位都会发生系统性错位。

### 9.4 为什么视觉、声景和活动性要分层建模

因为城市环境质量不是单模态现象：

1. 视觉好不代表声景好。
2. 热闹不代表舒适。
3. 绿视率高也不一定活力强。

分层建模比“一个总分”更科学。

### 9.5 为什么 Step 7.5 强调 leakage-safe、重复 CV 和 bootstrap

因为当前问题是典型的小样本、多特征、多目标场景。若不防信息泄漏、不给稳定性区间，模型很容易产生虚高结论。

### 9.6 为什么 design 不是直接拿模型分数排序

因为街道治理是行动问题，而不是纯预测问题。模型只能提供证据，最终排序必须结合：

1. 人评语义
2. 诊断严重度
3. 街道类型
4. 多模态一致性
5. 证据齐备度

### 9.7 为什么 deliverable 要合并成 episode

因为空间治理的真实对象往往是连续路段，而不是很多离散片段编号。

### 9.8 为什么 GIS / Web 不能反向决定分析结果

因为地图和网页是消费层。它们负责表达，不负责定义结论。这样才能避免“为了显示好看而篡改分析事实”。

## 11. 当前系统中的关键现实约束

### 11.1 坐标系约束

当前权威坐标系是 `GCJ-02`。若网页或 GIS 采用 `WGS84`，必须明确说明那是派生值而不是原始权威坐标。

### 11.2 人工评分约束

如果没有 `final_annotation_labels_adjudicated.csv`，系统可以完成基础分析、空间对齐、多模态汇总，但无法正式完成 Step 7.5、design 和 deliverable 的完整监督闭环。

### 11.3 Agents 不是最终裁决者

多智能体诊断是可解释证据层，不是最终真值标签层。它不能替代 validation。

### 11.4 GIS 平滑与真实路径的边界

网页和 GIS 显示层可以做轻量平滑和渲染优化，但不能随意篡改底层真实坐标。显示平滑只能服务于可读性，不能以偏离真实位置为代价。

## 13. 总结

当前项目不是“几个脚本加几个图表”的松散集合，而是一条完整的、分层清晰的技术链路：

1. 用真实分析帧建立可复核观测。
2. 用真实 `segment_id` 串起多模态证据。
3. 用 `geo_sync` 赋予空间位置。
4. 用 `soundscape + visual + fusion + agents` 累积解释性证据。
5. 用人工评分文件定义问题语义。
6. 用 Step 7.5 建立稳健的模型证据层。
7. 用 design 将证据转成 segment 级优先级。
8. 用 deliverable 将高优先级 segment 合并为连续问题街道。
9. 用 relationship、group_confirmatory、proof 与 paper_figures 把研究证据压缩成正式图表。
10. 用 GIS 与网页把结果输出到可消费层。

因此，当前系统识别“问题街道”的逻辑并不是单点黑箱，而是：

**多模态证据 + 人类监督 + 泄漏安全建模 + 透明规则排序 + 连续路段合并**。

这正是它在工程上可落地、在科学上可解释、在治理上可使用的原因。

### 14.7 过程性中间图像资产说明

当前项目还会在若干目录中产生大量“过程性可视化资产”，用于 QA、人工复核或网页辅助展示，例如：

1. 人数检测逐帧结果图。
2. 语义分割叠加图。
3. 全景重投影中间图。
4. 音频波形图、频谱图、事件条形图。
5. 旧版基础统计图与交互式 HTML 图表。

这类资产的共同特征是：

1. 数量往往按 frame 成百上千，不适合作为“正式图表”逐张编目。
2. 它们主要服务于工程 QA，而不是最终研究结论或交付结论。
3. 它们的数据源通常直接是 `frames/frame_*.jpg`、原始音频波形、逐帧检测 txt/CSV 和基础统计 CSV。

如果后续需要，我可以再把这一类“过程性图像资产”单独整理成第二份附录。
